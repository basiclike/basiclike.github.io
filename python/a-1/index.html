1강. 직접 짜 보는 이유

설명 강의 ⏱ 약 20분

학습 목표

  • 읽지 못하는 코드를 고칠 때마다 다시 맡겨야 하는 이유
  • Claude가 고친 줄을 받아들일지 판단하려면 읽어야 하는 이유
  • 키오스크를 직접 다시 짜는 여섯 묶음의 길

Claude가 다 만들어 줬는데

→ Claude가 키오스크를 다 만들어 준 뒤에도 왜 코드를 직접 짜야 하는지 생각해 봅니다.

❓ 질문 Claude가 키오스크를 만들어 주는데, 왜 제가 Python을 직접 짜야 할까요?

Claude Code 과정에서 여러분은 Claude에게 카페 키오스크를 만들게 했습니다. 화면을 만들고, 담기와 품절과 결제를 하나씩 만들게 해서 kiosk/app.js 파일에 동작하는 키오스크가 생겼습니다.

이 질문에는 이렇게 답하는 것이 가장 자연스럽습니다. "Claude가 만들어 주니 직접 짤 필요가 없다"는 답입니다. 필요한 기능을 말로 설명하면 코드가 나오는데 문법을 따로 공부할 이유가 없어 보입니다.

Claude를 쓰지 말라는 이야기가 아닙니다. 앞으로도 Claude에게 맡길 일은 계속 맡깁니다. 이 과정이 묻는 것은 맡긴 뒤에 코드를 받은 쪽이 무엇을 할 수 있어야 하는지입니다.

Claude가 다 만들어 줬다는 것은 여러분이 그 코드를 읽을 수 있다는 뜻이 아닙니다.

그 코드를 지금 몇 줄이나 읽을 수 있을까요? 직접 세어 보겠습니다.

Claude가 만든 키오스크 코드 읽어 보기

→ Claude가 만든 코드에서 내가 읽을 수 있는 줄을 세어 보고, 읽지 못하는 코드를 고쳐야 할 때 어떤 일이 생기는지 알아봅니다.

발췌 코드에서 읽히는 줄 세기

아래는 app.js에서 주문 부분만 뽑은 코드입니다. 메뉴를 담은 배열(여러 값을 순서대로 묶어 둔 것), 품절 검사, 합계 계산이 들어 있습니다. 같은 일을 하는 부분만 뽑았기 때문에 여러분의 app.js와 글자는 다를 수 있습니다.

const menus = [
  { name: "아메리카노", price: 4500, soldOut: false },
  { name: "카페라테", price: 5000, soldOut: false },
  { name: "바닐라라테", price: 5500, soldOut: true },
];

const cart = [];

function addToCart(index) {
  const item = menus[index];
  if (item.soldOut) {
    alert(item.name + "는 품절입니다");
    return;
  }
  cart.push(item);
}

function getTotal() {
  let total = 0;
  for (const item of cart) {
    total += item.price;
  }
  return total;
}

위에서 아래로 한 줄씩 읽으면서, 그 줄이 무슨 일을 하는지 한 문장으로 말할 수 있으면 1을 세어 봅니다. Claude에게 묻지 않고 혼자 해 봅니다.

줄을 하나씩 세기가 어려우면 세 줄만 가리켜 봅니다.

  • 메뉴 세 개가 적힌 줄
  • 품절이면 메뉴를 담지 않고 멈추는 줄
  • 가격을 하나씩 더해 합계를 만드는 줄

세 줄을 다 가리키지 못해도 이상한 일이 아닙니다. 여러분은 아직 코드를 읽는 연습을 하지 않았기 때문입니다. 문제는 센 숫자가 아니라 이 코드를 고쳐야 하는 날에 생깁니다.

가게를 열어 보니 합계가 가끔 맞지 않는다는 말이 나왔다고 해 봅시다. 코드를 읽을 수 없으면 할 수 있는 일은 하나입니다. Claude에게 "합계가 이상해요. 고쳐 주세요."라고 다시 맡기는 일입니다.

고쳤다는 답이 오면 정말 고쳐졌는지는 화면을 눌러 보는 것 말고는 확인할 방법이 없습니다. 그래도 이상하면 같은 말을 한 번 더 보냅니다.

읽지 못하는 코드는 고칠 일이 생길 때마다 다시 맡기는 수밖에 없습니다.

회로도를 고쳐 달라는 요청 다시 보기

이 장면은 앞 과정에서 본 적이 있습니다. 개발자로 가는 길 5강 「AI 결과를 고치려면」에서 AI가 그려 준 회로도를 고쳐 달라는 요청을 받았다고 생각해 봤습니다. 회로를 모르면 어디를 어떻게 고칠지도, 고쳐진 회로가 맞는지도 가려낼 수 없었습니다.

회로도 자리에 여러분의 app.js를 넣어도 같은 이야기입니다.

  회로도 수정 요청 키오스크 수정 요청
받은 것 AI가 그린 회로도 Claude가 만든 app.js
요청 "회로도의 일부를 고쳐 주세요." "합계가 이상하니 고쳐 주세요."
읽지 못하면 어디를 고칠지, 고친 것이 맞는지 가려내지 못합니다 어디를 고칠지, 고친 것이 맞는지 가려내지 못합니다

그 강의는 이렇게 이어졌습니다. ==AI에만 기대면 여러분도 같은 상황에서 아무것도 하지 못하는 사람이 됩니다.==

AI가 만들어 주어도, 그것을 고치고 책임지는 일은 그 분야를 배우고 일해 본 사람의 몫입니다. 키오스크 코드에서는 그 몫을 지려면 코드를 읽을 수 있어야 합니다.

그런데 코드를 고치는 일은 가끔 있는 일입니다. 매일 하는 일에서는 어떨까요?

만들어 달라는 요청 다음에 할 일

→ 만들어 달라는 요청이 공부의 끝이 아니라 첫 줄인 이유와, Claude가 고친 줄을 판단하려면 무엇이 필요한지 알아봅니다.

공부의 첫 줄

Claude가 만들어 준 코드가 잘 움직이면 일은 끝난 걸까요?

"움직이면 끝"이라고 생각하기 쉽습니다. 개발자로 가는 길 7강 「만든 뒤에 배우는 순서」는 그렇지 않다고 했습니다. ==만들어 달라는 요청은 공부의 끝이 아니라 첫 줄입니다.==

그 강의의 학생 C와 학생 B는 같은 회비 정리 앱을 AI에게 받았습니다. 한 달 뒤 회원이 늘고 회비 합계가 맞지 않는 오류가 생겼습니다.

  학생 C 학생 B
만든 뒤에 한 일 잘 움직이니 바로 사용 기능 확인, 이유 질문, 화면과 처리와 저장의 구조 메모
합계가 맞지 않을 때 같은 요청 문장만 다시 입력 구조 메모에서 합계를 처리하는 자리를 짚어 질문
앱을 맡을 수 있는가 어렵습니다 맡을 수 있습니다

학생 C가 한 일은 앞에서 본 "합계가 이상해요. 고쳐 주세요."를 되풀이하는 일과 같습니다. 학생 B가 합계를 처리하는 자리를 짚을 수 있었던 것은 앱의 안을 알고 있었기 때문입니다.

키오스크에서 그 자리는 합계를 더하는 for 줄입니다. 이 줄을 짚어 묻는 일이 코드에서는 읽을 줄 아는 사람만 할 수 있습니다.

Claude가 고친 줄을 판단하려면

Claude가 코드를 고쳐 왔을 때, 받아들일지는 무엇을 보고 정할까요?

"실행해 보고 되면 받아들인다"는 답이 먼저 떠오릅니다. 한 번 눌러 본 화면은 고쳐 달라고 한 부분이 나아졌는지만 보여 줍니다. Claude가 다른 줄까지 바꿨는지는 화면에 나오지 않습니다.

그래서 AI Engineering 4강 「diff 확인과 커밋」에서는 고친 diff를 줄마다 읽고 계획한 변경만 커밋했습니다. diff는 고치기 전과 고친 뒤를 줄마다 보여 주는 화면입니다. 지운 줄은 -, 더한 줄은 +로 시작합니다.

Claude가 "품절 안내를 정리했습니다"라고 보고하며 고쳐 온 diff가 아래와 같다고 해 봅시다. 가상의 예입니다.

 function addToCart(index) {
   const item = menus[index];
-  if (item.soldOut) {
+  if (!item.soldOut) {
     alert(item.name + "는 품절입니다");
     return;
   }

바뀐 것은 한 줄입니다. 읽을 수 있으면 품절이면 멈추던 조건이 품절이 아니면 멈추는 조건으로 뒤집혔다는 것이 보입니다. 그대로 받아들이면 품절인 바닐라라테는 담기고 멀쩡한 아메리카노는 담기지 않습니다. 읽을 수 없으면 -와 + 두 줄만 보고 보고서의 말을 믿을지 말지 정해야 합니다.

팀 과제에서 조원이 고쳐 올린 부분을 읽지 않고 제출 버튼을 누르는 일과 같습니다. 읽지 않은 부분은 맞는지 틀린지 모른 채 내 이름으로 나갑니다.

Claude에게 맡기는 일이 늘수록 고친 줄을 받아들이거나 거절하는 판단은 읽을 수 있는 여러분의 몫이 됩니다.

그렇다면 어디서부터 짜 볼까요?

이 과정에서 갈 길

→ 환경을 만드는 데서 시작해 키오스크를 직접 다시 짜기까지 어떤 길로 가는지 봅니다.

[이미지: 1강-01 — 기술 그림.] ▲ 과정의 여섯 묶음이 환경, 데이터, 흐름, 묶기, 키오스크, 나누기로 이어져 키오스크에 닿는 길

여섯 묶음을 차례로 지나면 키오스크에 닿습니다.

  • 환경(2~6강): Python이 실행될 환경을 만들고 VS Code로 첫 코드를 실행하고 오류를 읽습니다.
  • 데이터(7~11강): 메뉴를 변수에 담고, 입력과 출력, 숫자, 문자열을 다루고, 순서도를 읽습니다.
  • 흐름(12~15강): 조건에 따라 실행할 줄을 고르고, 같은 일을 되풀이하는 코드를 짭니다.
  • 묶기(16~20강): 여러 값과 계산을 리스트, 함수, 클래스로 묶고 디버거로 값을 따라갑니다.
  • 키오스크(21~24강): 요구사항에서 키오스크를 설계하고 구현한 뒤 쿠폰 기능을 더합니다.
  • 나누기(25~26강): 패키지를 더하고 GitHub로 팀원에게 넘겨 팀원의 컴퓨터에서 실행합니다.

키오스크를 다시 짜는 것은 Claude가 만든 것과 똑같은 것을 갖기 위해서가 아닙니다. 같은 일을 내 손으로 짜 보면 Claude가 짠 코드를 거꾸로 읽는 눈이 생기기 때문입니다.

그래서 22강에서 app.js를 다시 엽니다. 방금 읽히지 않던 조건문, 반복문, 리스트가 어느 줄인지는 그때 알아봅니다.

이 과정은 환경, 데이터, 흐름, 묶기를 거쳐 키오스크를 직접 다시 짜고, 끝에서 Claude의 코드와 비교합니다.
