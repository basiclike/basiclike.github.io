문법을 다 알면 프로그램을 만들 수 있을까

→ 문법을 다 배운 뒤 작은 프로그램을 만들면 어떤 질문이 생기는지 생각해 봅니다.

문법만으로 만들 수 있는 프로그램

Python 문법을 처음부터 끝까지 다 배웠다고 해 봅시다. 변수, 조건문, 반복문, 함수, 클래스까지 시험 문제라면 막힘없이 풉니다.

❓ 질문 그러면 이제 프로그램을 만들 수 있을까요?

"문법을 다 알면 만들 수 있다"는 것이 처음 배우는 사람이 가장 먼저 하는 생각입니다. 이 생각이 맞는지 알아보려면 작은 프로그램을 실제로 만든다고 생각해 보는 것이 가장 빠릅니다. 처음부터 거창한 프로그램일 필요는 없습니다.

두 수를 더하는 계산기부터 창을 띄우는 프로그램까지, 만들려는 프로그램이 커질수록 알아야 할 것이 이렇게 늘어납니다.

만들 프로그램 알아야 하는 것
두 수를 받아 더하는 계산기 입력, 연산, 조건문, 함수
번호를 눌러 기능을 고르는 메뉴 프로그램 조건문, 반복문, 잘못 입력한 값을 다루는 법
다운로드 폴더의 파일을 종류별로 나눠 옮기는 파일 정리 프로그램 파일 경로를 적는 법, 운영체제마다 경로의 모양이 다른 이유
표로 된 자료를 읽어 평균을 내는 데이터 분석 예제 Python에 처음부터 들어 있지 않은 외부 라이브러리를 설치하는 법
창과 버튼이 있는 화면(GUI) 프로그램 화면을 짜는 법, 창을 띄우는 라이브러리가 내 컴퓨터에서 실행되는지

계산기와 메뉴 프로그램까지는 문법만으로 만들 수 있습니다. 파일 정리 프로그램부터는 이야기가 달라집니다. 경로, 운영체제, 외부 라이브러리처럼 문법 책이 다루지 않는 것을 알아야 합니다.

만들다 보면 생기는 질문

작은 프로그램이라도 직접 만들기 시작하면, 문법만 공부할 때는 한 번도 떠오르지 않던 질문이 생깁니다.

  • 이 코드는 어디에서 써서 저장해야 하지?
  • 지금 이 코드를 실행하는 Python은 어느 Python이지?
  • 필요한 라이브러리는 어떻게 설치하지?
  • 친구의 컴퓨터에서도 실행되게 하려면 무엇을 함께 보내야 하지?
  • 파일이 많아지면 폴더를 어떻게 나눠야 하지?

다섯 질문은 차례로 코드를 쓰는 도구, 코드를 실행하는 언어의 버전, 라이브러리를 설치하고 관리하는 일, 다른 사람의 컴퓨터에서도 같게 실행되는지, 파일을 정리하는 일을 묻고 있습니다. 어느 것도 문법 책의 목차에는 없습니다. 그런데 실제 개발에서 날마다 만나는 질문은 오히려 이쪽입니다. 취업을 준비한다면 더욱 그렇습니다. 회사가 뽑으려는 사람은 문법을 많이 외운 사람이 아니라 실제로 동작하는 프로그램을 만들 수 있는 사람이기 때문입니다.

이 질문들은 이론만 공부해서는 생기지 않습니다. 프로그램을 직접 만들어 실행해 봐야 생깁니다.

코드와 함께 준비할 것: 개발 환경

프로그램은 코드만으로 완성되지 않습니다. 코드를 쓰고, 실행하고, 시험하고, 다른 사람에게 건네는 데 필요한 것들이 함께 갖춰져야 비로소 코드가 프로그램이 됩니다.

이렇게 코드와 함께 준비해야 하는 것들을 묶어 개발 환경이라고 부릅니다.

Python 강의가 문법 앞에 개발 환경부터 다루는 이유도 여기에 있습니다. 문법을 배울 때마다 그 문법으로 작은 프로그램을 만들어 실행해 볼 자리가 먼저 있어야 하기 때문입니다.

↓ 이어서 같은 프로그램을 쓰는 사람과 만드는 사람은 서로 다른 것을 볼까요?

사용자와 개발자는 무엇을 다르게 볼까

→ 같은 프로그램을 놓고 쓰는 사람과 만드는 사람이 서로 다른 질문을 한다는 것을 알아봅니다.

같은 Chrome을 두고 다르게 묻는 두 사람

여러분이 매일 쓰는 Chrome 브라우저로 두 사람의 눈을 비교해 보겠습니다.

여러분은 Windows 노트북에서도, 회사의 Mac에서도, 스마트폰에서도 Chrome을 씁니다. 쓰는 사람에게는 셋이 모두 같은 Chrome입니다. 설치 파일을 다운로드해 실행하면 깔리고, 아이콘을 클릭하면 열립니다. 사용자의 관심은 "설치하면 실행된다"에서 끝나고, 사용자라면 그것이 당연합니다.

이제 여러분이 Chrome을 만드는 회사의 개발자라고 해 봅시다. Windows에서 새 기능을 하나 만들고 시험까지 마쳤습니다. 이 기능이 macOS에서도, Linux에서도, 스마트폰에서도 똑같이 동작할까요?

꼭 그렇지는 않습니다. 운영체제가 다르면 프로그램을 실행하는 방식, 파일을 저장하는 위치, 권한을 다루는 방식, 화면을 그리는 방식, 설치 파일을 나눠 주는 방식이 모두 달라질 수 있기 때문입니다. 그래서 개발자는 "내 Windows에서 잘 실행된다"에서 멈출 수 없고, 다른 사람의 컴퓨터에서도 같게 동작하는지, 배포한 뒤에도 안정적으로 실행되는지를 함께 물어야 합니다.

  • 사용자: "실행되는가?"
  • 개발자: "어떤 환경에서 실행되는가?"

==같은 Chrome을 놓고 사용자는 실행되는지를 묻고, 개발자는 어떤 환경에서 실행되는지를 묻습니다.==

초급과 중급을 가르는 기준

이 차이는 개발자 사이에서도 다시 나타납니다. 개발을 처음 배울 때는 코드 한 줄 한 줄의 기능에 집중하는 것이 자연스럽습니다. 내가 쓴 코드가 내 컴퓨터에서 실행되면 일을 다 한 것 같습니다.

하지만 실제 개발에서 내 코드는 동료의 컴퓨터에서도 실행되어야 하고, 팀 프로젝트 안에서 다른 사람의 코드와 함께 동작해야 하며, 서버나 사용자의 컴퓨터에 배포된 뒤에도 안정적으로 유지되어야 합니다.

구분 초급 개발자 중급 개발자
집중하는 것 코드가 실행되는지 코드가 안정적으로 실행될 환경까지
일을 다 했다고 보는 때 내 컴퓨터에서 실행될 때 동료의 컴퓨터, 팀 프로젝트, 배포한 서버에서도 안정적으로 실행될 때

"기능을 만들었다"에서 끝내지 않고 그 기능이 어디서나 실행되도록 환경까지 챙기는 것이, 초급에서 한 단계 올라서는 기준입니다.

↓ 이어서 코드는 내 컴퓨터에 멀쩡히 있는데, 환경이 다르다고 왜 실행이 안 될까요?

같은 문서가 컴퓨터마다 다르게 열리는 이유

→ 문서 파일이 새 버전의 프로그램에서 그대로 열리기도 하고 달라지기도 하는 이유를 보며, 실행 환경이 무엇인지 알아봅니다.

예전 문서는 새 프로그램에서 그대로 열린다

몇 년 전 Word 2010에서 만든 보고서 .docx 파일을 지금 Word 365에서 열면 어떻게 될까요? 대부분 아무 문제 없이 열립니다. 글자도, 표도, 기본 서식도 그대로입니다.

Word가 예전 버전에서 만든 문서를 새 버전에서도 열 수 있도록 맞춰 가며 발전해 왔기 때문입니다. 이렇게 새 버전이 예전 버전의 결과물을 그대로 받아 주는 성질을 하위 호환성(backward compatibility)이라고 합니다.

실행되는 기능이 든 문서는 환경에 따라 달라진다

그런데 문서 안에 "실행되는 것"이 들어 있으면 이야기가 달라집니다. PowerPoint 2013에서 만든 .pptx 발표 자료에는 애니메이션이, Excel 2016에서 만든 .xlsm 파일에는 클릭 한 번에 계산을 대신 해 주는 매크로가 들어 있을 수 있습니다.

두 파일을 365에서 열면 파일 자체는 열립니다. 하지만 애니메이션이 다르게 움직이거나, 매크로가 보안 설정 때문에 막히거나, 다른 파일과 연결해 둔 기능이 동작하지 않을 수 있습니다. 파일은 그대로인데 그 파일을 실행하는 프로그램의 버전, 보안 정책, 운영체제 설정이 달라졌기 때문입니다. 이렇게 실행하는 쪽이 달라져 생기는 문제를 호환성 문제라고 합니다.

이 장면을 셋으로 나눠 보면 이렇습니다.

나눈 것 예 다른 환경에서 열면
문서의 내용 글자, 표, 슬라이드 어디서나 비슷하게 열립니다.
실행되는 기능 애니메이션, 매크로 환경이 맞아야 제대로 동작합니다.
실행 환경 프로그램 버전, 보안 정책, 운영체제 설정 실행되는 기능이 동작할지를 정합니다.

소스 코드는 매크로가 든 파일과 같다

프로그램의 소스 코드는 처음부터 끝까지 "실행되는 기능"만 담은 문서입니다. 그러니 매크로가 든 Excel 파일과 같은 처지에 놓입니다. 소스 코드 파일이 내 폴더에 멀쩡히 있어도, 그 코드에 맞는 언어 버전, 라이브러리, 운영체제, 설정이 함께 있어야 실행됩니다.

코드가 있다는 것과 코드가 실행된다는 것은 다른 문제입니다.

↓ 이어서 이 말은 Python 코드에서도 정말 맞을까요?

Python 코드가 환경에 따라 멈추는 이유

→ Python 버전과 패키지 버전이 코드의 실행에 어떤 영향을 주는지 살펴봅니다.

C, C++, C#, Java 같은 언어는 기존 코드가 오래 동작하도록 설계하는 편입니다. 수십 년 전에 쓴 C 코드가 새 표준에서도 대체로 그대로 컴파일됩니다.

Python도 하위 호환성을 생각하며 발전합니다. 다만 실제 Python 개발에서는 문법만 맞아서는 부족하고, 여러 요소의 조합이 함께 맞아야 합니다.

요소 예
Python 버전 3.12, 3.14, 3.15
패키지 버전 NumPy, pandas, PySide6, PyTorch의 버전
운영체제 Windows, Ubuntu, macOS
실행하는 Python의 종류 시스템 Python, 전역 Python, 가상환경 Python

이 가운데 가장 먼저 부딪히는 것이 Python 버전과 패키지 버전입니다.

언어 버전이 바뀌면

[이미지: 1강-01 — 기술 그림.] ▲ 같은 코드가 두 환경에서 한쪽은 실행되고 한쪽은 멈춥니다.

아래는 0부터 999999까지의 수를 모두 더하는 데 시간이 얼마나 걸리는지 재는 코드입니다. 예전에 널리 쓰던 time.clock()이라는 함수로 시간을 잽니다. timer.py라는 이름으로 저장했다고 해 봅시다.

import time

start = time.clock()
total = 0
for n in range(1000000):
    total = total + n
end = time.clock()

print("합계:", total)
print("걸린 시간:", end - start, "초")

지금은 코드를 한 줄 한 줄 이해하지 못해도 괜찮습니다. 이 파일 하나를 한 컴퓨터에서는 Python 3.7로, 다른 컴퓨터에서는 지금 널리 쓰는 Python 3.14로 실행한다고 해 봅시다. "코드가 같으니 결과도 같다"고 생각하기 쉽습니다.

Python 3.7에서는 time.clock()이 있으므로 코드가 끝까지 실행되어 합계와 걸린 시간이 나옵니다. Python 3.14에서는 3번째 줄에서 멈추고 이런 오류가 나옵니다.

Traceback (most recent call last):
  File "...\timer.py", line 3, in <module>
    start = time.clock()
            ^^^^^^^^^^
AttributeError: module 'time' has no attribute 'clock'

파일 경로는 컴퓨터마다 다르므로 ...로 줄여 썼습니다. 마지막 줄은 "time 모듈에 clock이라는 것이 없다"는 뜻입니다.

이런 일이 생기는 이유는 import time으로 불러오는 time 모듈이 여러분이 만든 것이 아니기 때문입니다. time 모듈은 Python을 설치할 때 함께 깔리는 표준 라이브러리이고, 표준 라이브러리는 Python 버전마다 따로 들어 있습니다. Python을 만드는 사람들은 3.3 버전부터 time.clock()을 쓰지 말라고 안내했고, 3.8 버전에서 이 함수를 지웠습니다. 공식 문서는 그 대신 time.perf_counter()나 time.process_time()을 쓰라고 안내합니다. 지금의 time 모듈 문서에는 clock() 항목이 아예 없습니다.

안내대로 두 줄을 time.perf_counter()로 고치면 Python 3.14에서 이렇게 실행됩니다.

import time

start = time.perf_counter()
total = 0
for n in range(1000000):
    total = total + n
end = time.perf_counter()

print("합계:", total)
print("걸린 시간:", end - start, "초")

합계: 499999500000
걸린 시간: 0.043880799999897135 초

걸린 시간은 실행할 때마다 조금씩 다르게 나옵니다.

표준 라이브러리라고 해서 영원히 바뀌지 않는 것은 아닙니다. Python은 계속 새 버전이 나오고, 옛 버전은 지원이 끝납니다. 지금의 최신 안정 버전은 3.15이고, 3.10은 2026년 10월 1일에 지원이 끝났습니다.

Python 버전 지금의 상태
3.15 최신 안정 버전입니다.
3.14 버그 수정을 하며 2030년 10월까지 지원합니다.
3.13, 3.12, 3.11 보안 수정만 하며 각각 2029년 10월, 2028년 10월, 2027년 10월까지 지원합니다.
3.10과 그보다 옛 버전 지원이 끝났습니다.

그래서 오래된 글이나 옛 코드를 가져다 쓰면, 그 코드가 쓰던 Python과 지금 내 컴퓨터의 Python이 다를 수 있습니다. 어느 Python으로 실행하느냐가 성공과 실패를 정합니다.

패키지 버전이 맞지 않으면

Python에서는 따로 설치해 쓰는 코드 묶음(패키지)을 많이 가져다 씁니다. 숫자 계산에는 NumPy, 표 데이터에는 pandas, 창을 띄우는 화면에는 PySide6, 인공지능 학습에는 PyTorch를 쓰는 식입니다. 이 패키지들도 저마다 버전이 있고, 버전이 올라가며 사용법이 바뀝니다.

첫 번째 경우는 패키지의 사용법이 바뀌는 것입니다. 예를 들어 NumPy에서 np.int나 np.float로 쓰던 표현은 NumPy 버전이 올라가며 제거되어, 지금은 오류가 납니다.

두 번째 경우는 패키지가 Python 버전을 요구하는 것입니다. Python이 새 버전으로 나와도 모든 패키지가 그날부터 새 버전을 지원하지는 않습니다. 반대로 새로 나온 패키지는 오래된 Python을 더 이상 지원하지 않기도 합니다.

두 경우가 겹치면 조합이 묶여 버립니다. 오래된 코드가 np.int를 쓰면 그 코드를 실행하려고 예전 NumPy를 설치해야 하고, 예전 NumPy는 예전 Python에서만 설치될 수 있습니다. 하나를 고르면 다른 하나가 따라 정해지는 셈이라, 그 프로젝트는 "이 Python과 이 NumPy"라는 한 조합에 묶입니다.

그래서 프로젝트마다 맞는 Python과 패키지가 다릅니다.

프로젝트 맞는 Python 버전 쓰는 패키지
데이터 분석 3.12 pandas, NumPy
화면(GUI) 프로그램 3.13 PySide6
인공지능 학습 3.12 PyTorch

세 프로젝트는 예를 든 것이고, 실제로 맞는 버전은 패키지가 지원하는 범위에 따라 달라집니다.

세 경우를 묶으면 결론은 하나입니다.

Python 프로그램은 코드만 맞아서는 실행되지 않고, Python 버전과 패키지 버전의 조합이 맞아야 실행됩니다.

==내 컴퓨터에서는 되는데 다른 컴퓨터에서는 안 된다면, 원인은 대개 코드가 아니라 두 컴퓨터의 조합이 다른 데 있습니다.==

↓ 이어서 이 조합 문제는 컴퓨터 두 대 사이에서만 생길까요?
한 컴퓨터 안에서는 어떨까요?

두 프로젝트가 한 Python을 함께 쓰면

→ 한 컴퓨터에서 두 프로젝트가 Python 하나를 함께 쓸 때 무슨 일이 생기는지 보고, 환경을 나누는 방법을 알아봅니다.

한쪽을 올리자 다른 쪽이 멈춘 이야기

조합 문제가 한 컴퓨터 안에서 어떻게 터지는지 개발자 C의 이야기로 보겠습니다.

개발자 C의 컴퓨터에는 Python 3.12가 하나 깔려 있고, 그 Python에 PySide6의 한 버전을 설치해 두었습니다. 개발자 C는 이 Python으로 창을 띄우는 A 프로젝트를 만들었고, A 프로젝트는 아무 문제 없이 실행됩니다.

얼마 뒤 개발자 C는 새 B 프로젝트를 맡았습니다. B 프로젝트는 더 새 Python 3.14와 PySide6의 새 버전을 써야 합니다. 개발자 C는 "컴퓨터의 기본 Python을 3.14로 바꾸고 PySide6도 새 버전으로 올리면 되겠다"고 생각하고 그대로 했습니다. B 프로젝트는 잘 실행됩니다.

그다음 날 개발자 C가 A 프로젝트를 다시 실행하면 어떻게 될까요? "A 프로젝트는 아무 일 없다"고 생각하기 쉽습니다. 기본 Python을 원하는 버전으로 바꾸면 된다는 흔한 생각을 따라간 것입니다.

그런데 개발자 C가 바꾼 것은 B 프로젝트만의 환경이 아니라 두 프로젝트가 함께 쓰던 Python이었습니다. A 프로젝트는 이제 만들 때와 다른 Python과 PySide6 조합으로 실행됩니다. 앞에서 본 time.clock()처럼 A 프로젝트가 기대던 기능이 새 버전에서 바뀌었거나 사라졌다면, 어제까지 잘 되던 기능에서 멈춥니다. 코드는 한 글자도 고치지 않았는데도 그렇습니다.

기본 Python 하나를 바꾸면, 그 Python을 쓰던 모든 것이 함께 바뀝니다.

한 컴퓨터에 있는 세 종류의 Python

[이미지: 1강-02 — 기술 그림.] ▲ 운영체제 위에 시스템 Python과 전역 Python이 있고, 프로젝트 폴더마다 가상환경 Python이 따로 있습니다.

Python은 한 컴퓨터에 하나만 있지 않습니다. 쓰는 사람과 바꿔도 되는 범위에 따라 세 종류로 나눠 보면 쉽습니다. 아파트 현관의 도어락 비밀번호에 비유해 보겠습니다.

  • 시스템 Python: 운영체제나 다른 프로그램이 자기 일에 쓰는 Python입니다. 도어락에 비유하면 관리실이 정해 둔 마스터 비밀번호입니다. 입주자가 마음대로 바꾸면 관리실의 모든 일이 멈추므로 건드리지 않습니다.
  • 전역 Python: 여러분이 평소에 쓰는 Python입니다. 개발하려고 직접 설치하고, 명령을 입력하는 창(터미널)에서 기본으로 불리는 Python이 여기에 듭니다. 도어락에 비유하면 집 식구가 함께 쓰는 비밀번호입니다.
  • 가상환경 Python: 특정 프로젝트 안에서만 쓰는 독립된 Python 환경(가상환경, virtual environment)입니다. 프로젝트 폴더 안에 따로 만들어 두고, 그 프로젝트에 필요한 패키지 버전을 그 안에서만 관리합니다. 도어락에 비유하면 손님이나 수리 기사에게 하루 이틀만 쓰라고 내주는 임시 비밀번호입니다. 그 사람에게만 따로 주고, 일이 끝나 지워도 식구의 비밀번호와 마스터 비밀번호는 그대로입니다.

세 비밀번호의 쓰는 사람과 바꿔도 되는 범위가 저마다 다르듯, 세 Python도 쓰는 쪽과 바꿔도 되는 범위가 저마다 다릅니다.

시스템 Python이 왜 따로 있는지는 Ubuntu 같은 Linux에서 잘 보입니다. Linux는 관리 도구와 프로그램 설치 기능의 일부가 Python으로 쓰여 있어서 처음부터 Python이 깔려 있습니다. 그래서 개발자가 "기본 Python을 원하는 버전으로 바꾸겠다"며 그 Python을 지우거나 다른 버전으로 바꾸면, 내 프로젝트 하나가 아니라 운영체제의 기능이 멈출 수 있습니다. ==시스템 Python은 운영체제의 일부이므로 바꾸지 않습니다.==

여러분의 Windows에서 시스템 Python에 가까운 것은, 다른 개발 도구가 자기 일에 쓰려고 함께 깔아 둔 Python입니다. 그 프로그램이 기대는 Python이니 손대지 않습니다.

개발자 C의 Python 3.12가 바로 전역 Python이었습니다. 두 프로젝트가 식구의 비밀번호 하나를 함께 쓴 셈이고, 그래서 한쪽을 위해 바꾸자 다른 쪽까지 바뀌었습니다.

프로젝트마다 환경을 나눈다

개발자 C의 문제는 서로 다른 조합이 필요한 두 프로젝트가 Python 하나를 함께 쓴 데서 생겼습니다. 그러니 해결은 나누는 것입니다.

시스템 Python은 그대로 둡니다. 전역 Python에는 Python 3.12와 3.14를 나란히 설치하되, 프로젝트의 패키지는 쌓지 않습니다. 대신 프로젝트마다 가상환경을 하나씩 만들어 그 프로젝트의 조합을 그 안에 둡니다.

프로젝트 가상환경에 둘 조합
A 프로젝트 Python 3.12와 PySide6의 예전 버전
B 프로젝트 Python 3.14와 PySide6의 새 버전

그러면 B 프로젝트에서 무엇을 올리든 A 프로젝트의 환경은 그대로입니다.

↓ 이어서 환경을 나누는 일은 숙련된 개발자만 쓰는 특별한 기법일까요?

정리

→ 환경을 나누는 일이 개발자의 기본 일이라는 것을 정리하고, 앞으로 이어질 강의에서 해 볼 일을 확인합니다.

코드가 실행되기까지 개발자가 챙길 것

환경을 나누는 일은 특별한 고급 기법이 아니라 Python 개발의 기본입니다. 프로그래밍의 목적은 문법을 아는 데 있지 않고 실제로 실행되는 프로그램을 만드는 데 있기 때문입니다.

📌 정리 코드가 있다는 것과 코드가 실행된다는 것은 다른 문제입니다. 코드가 실행되려면 Python 버전과 패키지 버전의 조합이 맞는 환경이 함께 있어야 합니다. 그 환경을 프로젝트마다 나눠 지키는 일은 개발자가 덤으로 하는 일이 아니라 기본 일입니다.
