홈 /3. Claude Work /A. 조사하고 문서로 받기

6강. Artifacts와 Docs로 보면서 고치기

실습 강의 ⏱ 약 45분

학습 목표

5강에서는 Claude가 만든 Word, Excel, PowerPoint 파일을 열어 요청과 맞춰 보고, 고칠 곳만 고치게 했습니다.
이번 강에서는 파일을 받아 오가지 않고, Claude가 만든 글을 한 장의 문서로 두고 보면서 고쳐 봅니다.

  • 긴 답을 조금 고쳐 달라고 했는데 새 답이 또 오면, 어느 답이 마지막 판이고 고치라고 하지 않은 곳이 그대로인지 어떻게 알 수 있을까요?
  • 대화의 답, 아티팩트, Docs는 어디에 저장되고 누구와 함께 고칠 수 있는지 알아봅시다.
  • 문서에서 고칠 문단과 줄만 골라 맡기면 다른 곳이 정말 그대로인지 직접 확인해 봅시다.
  • 링크를 받은 팀원은 내 문서를 어디까지 고칠 수 있는지 알아봅시다.
  • 함께 고친 조사 요약을 Markdown 파일로 꺼내 키오스크 폴더에 둬 봅시다.

고친 답이 새 답으로 오는 불편

→ 대화에 다시 요청하면 고친 결과가 어떻게 돌아오는지 보고, 한 장의 문서가 왜 필요한지 생각해 봅니다.

세 번째 답에서 길을 잃은 직원 A

사무실의 직원 A가 팀 행사 안내문을 Claude에게 받았다고 해 봅시다.
일정 표와 날마다 할 일, 준비물까지 화면을 두 번 내려야 끝나는 긴 답입니다.
다 읽고 나니 첫날 일정 문단이 너무 길었습니다.

직원 A는 "첫날 문단만 짧게 줄여 줘"라고 보냈습니다.
그러자 Claude가 새 답을 썼고, 직원 A는 위의 답과 아래의 답을 번갈아 내리며 무엇이 바뀌었는지 찾았습니다.
준비물 한 줄을 더해 달라고 하자 또 새 답이 왔습니다.

세 번째 답을 받았을 때 직원 A는 헷갈렸습니다.
어느 답이 마지막 판인지, 첫날 문단을 줄인 것이 마지막 답에도 남아 있는지 알 수 없었습니다.

고친 결과는 앞의 답 아래에 쌓입니다

5강에서 여러분은 Claude에게 Word, Excel, PowerPoint 파일을 받았습니다.
고칠 곳을 자리와 모양으로 적어 고치게 한 뒤, 고치기 전 파일과 고친 파일을 나란히 열어 비교했습니다.
그때 고친 파일은 고치기 전 파일과 따로 다시 왔습니다.

대화의 답도 마찬가지입니다.
대화에 다시 요청하면 Claude는 앞의 답을 고치지 않고 새 답을 씁니다.
고친 문단만 보내기도 하고 안내문 전체를 처음부터 다시 쓰기도 하지만, 어느 쪽이든 고친 결과는 앞의 답 아래에 따로 놓인 새 답입니다.
앞의 답은 그대로 남습니다.

그래서 고쳐 달라고 하지 않은 문단이 그대로인지는 새 답과 앞의 답을 나란히 놓고 맞춰 보아야만 알 수 있습니다.
대화의 답은 주고받은 말이 차례로 쌓이는 기록이지, 한 장의 문서가 아닙니다.

↓ 이어서 여러 번 고칠 글이라면 처음부터 한 장의 문서로 받을 수는 없을까요?

여행 안내문을 Docs로 만들기

→ Output에서 Docs를 골라 여행 안내문을 만들고, 그 문서가 어디에 저장되는지 찾아봅니다.

Output에서 Docs 고르기

여러 번 고칠 글은 처음부터 한 장의 문서로 받는 편이 낫습니다.
오늘은 Claude에게 그런 문서를 만들게 하는 Docs를 씁니다.
Docs는 Claude가 만든 문서를 내 Claude 계정에 저장해 두고, 나와 Claude가 같은 문서를 그 자리에서 고치는 기능입니다.

연습으로 가족 여행 안내문을 Docs로 만든 뒤, 키오스크 조사 요약을 Docs로 만들어 팀원과 함께 고쳐 봅니다.

▲ 입력창의 Output 메뉴에 만들 결과의 모양이 나열된 모습

① 데스크톱 앱에서 사이드바의 새 대화 버튼을 클릭해 새 대화를 엽니다.

② 입력창의 Output을 클릭합니다.

메뉴에 Docs, Slides, Design, Dashboards가 보이면 됩니다.
메뉴를 쓰지 않고 입력창 맨 앞에 /docs를 적은 뒤 요청을 이어 써도 같습니다.

여행 안내문 요청

아래 요청문을 입력하고 보냅니다.
요청문에는 문서의 차례와, 비워 둘 칸과, 지어내지 말 사실을 적었습니다.
5강에서 파일을 받을 때 조건을 먼저 적어야 받은 결과를 조건과 맞춰 볼 수 있었던 것과 같습니다.

가족 넷이 가는 부산 1박 2일 여행 안내문을 만들어 줘.

- 때: 2026년 11월 14일 토요일 아침 8시 서울역 출발, 15일 일요일 저녁 7시 서울역 도착
- 가는 길: KTX 왕복
- 첫날: 해운대 해변 산책, 점심은 해운대 근처 식당, 오후에 동백섬, 저녁에 광안리에서 광안대교 야경 보기
- 둘째 날: 감천문화마을, 점심은 남포동, 오후 4시 부산역 출발
- 준비물: 신분증, 편한 신발, 얇은 겉옷, 휴대전화 충전기

맨 위에 제목, 그다음 한눈에 보는 일정 표(날짜, 시간, 할 일, 장소), 날마다 자세한 일정, 준비물 목록, 연락처 칸의 차례로 써 줘. 연락처 칸은 비워 두고 "(직접 적기)"라고만 써 줘. 식당 이름, 기차 시간표, 입장료처럼 위에 적지 않은 사실은 지어내지 마.

Docs를 만들 때 Claude는 초안을 쓰기 전에 몇 가지를 먼저 물을 수 있습니다.
물으면 요청문에 적은 것 안에서 답합니다.
요청문에 없는 것(숙소, 식당 이름)을 물으면 "정하지 않았으니 비워 둬"라고 답합니다.

⚠ 확인 필요 이 요청문을 보냈을 때 Claude가 먼저 묻는지와 묻는 내용

Claude의 답과 만들어진 문서

문서가 다 만들어지면 대화에는 짧은 답이 오고, 문서는 대화 옆의 창에 열립니다.

⚠ 확인 필요 데스크톱 앱에서 Docs가 대화 옆 창으로 열리는지와 창의 모양

Claude가 실제로 낸 답은 아래와 같고, 그 아래의 표와 목록이 Docs에 만들어진 문서의 내용입니다.
문서 안에서는 표가 표로, 제목이 굵은 큰 글씨로 보입니다.

부산 여행 안내문을 Docs로 만들었습니다. 문서에 들어간 내용은 아래와 같습니다. 주신 정보에 없는 식당 이름, 기차 편명과 도착 시각, 입장료, 숙소는 적지 않았습니다.

[이미지: A-6-04 — 기술 그림.]
▲ 답, 아티팩트, Docs가 저장되는 곳과 함께 고치는지와 내보내는 형식을 비교한 표

지금까지 Claude가 만든 결과를 세 가지 모양으로 보았습니다.
2강부터 5강까지 받아 온 대화의 답, 오늘 Artifacts 탭에서 본 아티팩트, 그 아티팩트 가운데 하나인 Docs 문서입니다.

⚠ 확인 필요 사용자가 kiosk-research-report.docx를 올린 대화에서 이 요청을 보내 받은 결과로 채운다 — 대화의 짧은 답과, Docs "키오스크 개선 사례와 접근성 조사 요약"의 전체 내용(핵심 요약 세 줄, 국내 사례 표, 접근성 기준 정리, 확인이 필요한 부분, 팀원이 고칠 곳의 다섯 부분이 보여야 한다)과, 파일을 올린 대화에서 Output의 Docs가 그 파일을 근거로 문서를 만드는지

요약을 보고서와 대조하기

팀원에게 보내기 전에 요약을 보고서와 대조합니다.
요약은 짧고 그럴듯해 보여서, 보고서에 없던 말이 섞여도 눈에 잘 띄지 않습니다.
보고서를 Word로 열어 요약 옆에 나란히 둡니다.

2강에서 출처를 열어 줄마다 표시했듯이, 요약의 줄마다 셋 가운데 하나를 표시합니다.

표시 고르는 때
확인함 보고서에서 같은 내용을 찾았습니다
보고서에 없음 보고서에서 찾지 못했습니다
보고서와 다름 보고서와 값이나 뜻이 다릅니다

볼 곳은 다섯입니다.

  • 핵심 요약 세 줄: 보고서의 문장에서 나왔는지 봅니다.
  • 사례 표: 줄이 셋 이하이고, 어디서, 무엇을 바꿨나, 결과의 칸이 보고서와 같은지 봅니다.
  • 결과를 찾지 못한 사례: 보고서가 결과를 찾지 못했다고 한 사례의 결과 칸이 "결과 찾지 못함"인지 봅니다.
  • 수치와 제도: 기준일이 붙어 있고, 그 날짜가 보고서에 적힌 날짜와 같은지 봅니다.
  • 출처 링크: 하나씩 클릭해 열리는지, 보고서의 링크와 같은 주소인지 봅니다.

"보고서에 없음"이나 "보고서와 다름"을 표시한 줄이 있으면 그 줄을 골라 Edit with Claude로 보고서의 값으로 고치게 하고, 고친 뒤 다시 표시합니다.

⚠ 확인 필요 대조에서 나온 "보고서에 없음"이나 "보고서와 다름" 줄과 그 고친 결과

Share로 팀원에게 보내기

대조를 마쳤으면 팀원 이서연에게 이 문서를 보냅니다.
Docs는 처음 만들었을 때 나만 볼 수 있습니다.
이서연은 "팀원이 고칠 곳"을 고쳐야 하므로 Editor를 고릅니다.

[화면 캡처: A-6-11 — 조사 요약 Docs의 Share 화면. ① Share, ② 누가 열 수 있는지 고르는 곳, ③ Viewer와 Editor, ④ 링크 복사]
▲ Share 화면에서 링크를 가진 사람과 권한을 고르는 모습

① 문서 화면의 Share를 클릭합니다.

② 누가 열 수 있는지를 링크를 가진 사람으로 바꿉니다.

③ 권한을 Editor로 고릅니다.

④ 링크를 복사합니다.

복사한 링크는 메신저나 메일로 이서연에게 보냅니다.

⚠ 확인 필요 Docs의 Share 화면에 보이는 글자(Who has access, Only you, Anyone with the link, Viewer와 Editor인지 Can view와 Can edit인지)

Pro 요금제에서 Docs는 링크를 가진 사람과 나눕니다.
메일 주소로 한 사람씩 초대하는 방법은 Docs에 없습니다.
그러니 이서연이 링크를 다른 사람에게 넘기면 그 사람도 링크를 가진 사람이 됩니다.

다만 공유한 Docs를 열려면 누구든 Claude 계정이 있어야 합니다.
Claude 계정이 없는 사람은 링크를 받아도 열지 못합니다.

권한은 둘입니다.

권한 할 수 있는 일
Viewer 문서를 읽기만 합니다
Editor 읽고, 고치고, 댓글을 달고, 내보내기까지 합니다

댓글만 달게 하는 권한은 없습니다.
그래서 Editor 링크가 다른 곳으로 퍼지면 모르는 사람이 문서를 고치거나 파일로 꺼내 갈 수 있습니다.
함께 고칠 사람에게만 Editor 링크를 보내고, 읽기만 할 사람에게는 Viewer 링크를 따로 보냅니다.

⚠ 주의
휴대전화의 Claude 앱에서는 공유 설정을 바꾸지 못하므로 데스크톱 앱이나 웹에서 바꿉니다.
문서의 이름을 바꾸거나 지우는 것은 만든 사람만 할 수 있습니다.
지운 문서는 휴지통 없이 바로 없어지고 링크를 받은 사람도 더는 열지 못하므로, 팀원과 나눈 문서는 지우기 전에 한 번 더 생각합니다.

팀원이 고친 줄 다시 확인하기

이서연이 링크를 열어 "팀원이 고칠 곳"의 줄을 고칩니다.
함께 듣는 사람이 없으면 다른 Claude 계정으로 링크를 열어 이서연의 역할을 직접 합니다.
이서연이 고친 것은 저절로 저장되고, 문서를 열어 둔 내 화면에도 바로 나타납니다.

⚠ 확인 필요 팀원이 고친 곳이 내 화면에 보이는 모양과, 누가 고쳤는지 표시되는지

[화면 캡처: A-6-12 — 팀원이 "팀원이 고칠 곳"의 줄을 고친 뒤의 조사 요약 Docs. ① 팀원이 고친 줄, ② 고친 사람의 표시]
▲ 팀원이 고친 줄이 내 화면의 문서에 나타난 모습

팀원이 고쳤다고 끝이 아닙니다.
이서연이 고친 줄마다 보고서를 다시 열어 같은 표시(확인함, 보고서에 없음, 보고서와 다름)를 합니다.
==함께 고친 문서라도 팀에 내놓는 것은 나이고, 고친 줄이 보고서와 맞는지 확인하는 일은 사람에게 남습니다.==

Markdown 파일로 키오스크 폴더에 남기기

마지막으로 다 고친 요약을 Markdown 파일로 꺼냅니다.
Export에서 Markdown을 고르면 파일이 Downloads 폴더에 다운로드됩니다.

⚠ 확인 필요 다운로드한 Markdown 파일의 처음 이름과, 키오스크 폴더로 바로 저장할 수 있는지

① 문서 화면의 Export를 클릭합니다.

② Markdown을 클릭합니다.

③ File Explorer에서 Downloads 폴더를 열고 다운로드한 파일을 C:\kiosk-project로 끌어 옮깁니다.

④ 옮긴 파일을 오른쪽 클릭해 이름을 kiosk-research-summary.md로 바꿉니다.

[화면 캡처: A-6-13 — 메모장으로 연 kiosk-research-summary.md. ① 제목 앞의 #, ② 표의 |, ③ 창 위의 파일 이름]
▲ 메모장에서 Markdown 파일의 제목 앞 #과 표의 |가 글자로 보이는 모습

① 옮긴 파일을 오른쪽 클릭하고 Open with에서 메모장을 클릭합니다.

② 제목 앞의 #을 봅니다.

③ 표의 칸 사이에 있는 |를 봅니다.

문서에서 큰 글씨였던 제목 앞에 #이, 표의 칸 사이에 |가 글자로 보이면 됩니다.
Docs 화면에서 보기 좋게 나오던 문서가 사실은 이런 기호가 섞인 글자로 꺼내진다는 것을 눈으로 보아 둡니다.

⚠ 확인 필요 한국어 Windows에서 Open with와 메모장 메뉴의 글자

⚠ 확인 필요 내보낸 Markdown 파일에서 제목이 #으로, 표가 |로 적혀 있는지

이 파일은 10강에서 Word와 HWPX 파일과 나란히 메모장으로 다시 열고, 11강에서 이 기호들의 규칙을 배웁니다.

이렇게 하면 고칠 때마다 새 답을 뒤져 마지막 판을 찾지 않아도 됩니다.

그러나 문서가 보기 좋아졌다고 내용까지 맞는 것은 아닙니다.
고친 문단이 그 자리만 바뀌었는지, 요약의 줄이 보고서에 있는지, 팀원이 고친 줄이 보고서와 맞는지는 모두 여러분이 원본을 열어 확인했습니다.
