실습 강의 ⏱ 약 50분

학습 목표

14강에서 키오스크 자료와 지침을 Project "카페 키오스크 개선"에 모았습니다.
이제 키오스크 대화를 열 때마다 보고서를 다시 올리거나 프로젝트 범위를 다시 설명하지 않아도 됩니다.
그런데 되풀이하는 일이 하나 더 남아 있습니다.
이번 강의에서는 이 일을 Skill에 맡깁니다.

  • 문서를 만들어 달라고 할 때마다 조건을 덧붙이지 않아도 되게 하려면 어디에 무엇을 써 두어야 할지 알아봅시다.
  • Skill이 코드가 아니라 Claude가 읽는 문장이라는 것을 Skill 파일을 직접 열어 확인해 봅시다.
  • Claude는 Skill을 켤지 말지를 무엇만 보고 정하는지 알아봅시다.
  • Skill이 켜지면 안 되는 때를 어떻게 적어 두는지 알아봅시다.

# 만들기 전에 조건 묻기

사용자가 문서, 안내문, 조사 정리를 만들어 달라고 하면, 바로 만들지 말고 아래 다섯 조건이 요청에 들어 있는지 먼저 확인한다.

## 확인할 다섯 조건

| 조건 | 뜻 | 예 |
|---|---|---|
| 대상 | 누가 읽는지 | 팀장, 매장 점주, 고객 |
| 분량 | 얼마나 길게 쓰는지 | A4 한 장, 슬라이드 5장, 10줄 이내 |
| 형식 | 어떤 파일 종류로 내는지 | Word, 한글(hwpx), PDF, 메일 본문 |
| 마감 | 언제까지 필요한지 | 오늘 오후, 이번 주 금요일, 회의 하루 전 |
| 근거 자료 | 무엇을 바탕으로 쓰는지 | 올린 파일, 회의 메모, 설문 결과 |

## 순서

1. 요청 문장과 대화에 올라온 파일에서 다섯 조건 가운데 이미 정해진 것을 찾는다.
2. 빠진 조건이 있으면 한 번에 하나만 묻는다. 여러 조건을 한 질문에 묶지 않는다.
3. 물을 때는 사용자가 고를 수 있는 예를 두세 개 함께 보여 준다. 예: "누가 읽는 글인가요? (1) 팀장 보고용 (2) 매장 직원 공지용 (3) 고객 안내용"
4. 답을 받으면 다음 빠진 조건을 묻는다. 다섯 조건이 모두 정해질 때까지 반복한다.
5. 다섯 조건이 다 정해지면 정한 조건을 한 줄에 하나씩 다시 보여 준다.

   - 대상: …
   - 분량: …
   - 형식: …
   - 마감: …
   - 근거 자료: …

6. 그 뒤에 문서를 만든다.

## 지킬 것

- 빠진 조건을 짐작으로 채우지 않는다. 요청이나 대화에 없는 조건은 반드시 사용자에게 묻는다.
- 사용자가 "알아서 해"라고 답한 조건은 Claude가 정한 값을 보여 주고 그대로 써도 되는지 한 번 확인한다.
- 근거 자료가 "없음"이면 없다고 정한 것으로 보고, 다시 보여 줄 때 "근거 자료: 없음(일반 지식으로 작성)"처럼 적는다.

skill-name/

├── scripts/       넣지 않아도 되는 폴더. 실행할 코드
├── references/    넣지 않아도 되는 폴더. 필요할 때만 읽는 참고 문서
└── assets/        넣지 않아도 되는 폴더. 결과물에 쓰는 양식이나 그림

ask-before-start는 SKILL.md 하나만 있는 가장 단순한 Skill입니다.
코드가 있든 없든, 언제 무엇을 할지 정하는 것은 SKILL.md의 문장입니다.

▲ SKILL.md의 머리와 본문이 각각 읽히는 때

켜 둔 Skill의 name과 description은 모든 대화에 늘 놓여 있습니다.

맞는 것이 있으면 그때 그 Skill의 본문을 읽습니다.

그래서 Skill을 설계할 때 묻는 질문은 "무엇을 시킬까"만이 아닙니다.
"이 지시를 언제 적용할까, 언제 빼 둘까"를 함께 물어야 합니다.
본문을 아무리 잘 써도 description이 켜질 때를 잘못 말하면, 본문은 필요할 때 읽히지 않거나 필요 없을 때 읽힙니다.

답할 사람이 없는 실행

19강에서는 Claude에게 정해진 때마다 일을 하게 하는 예약을 만듭니다.
예약을 만들 때는 Claude가 고를 수 있는 답을 보여 주며 우리에게 물을 수 있다고 도움말에 적혀 있습니다.
실행될 때도 물을 수 있는지는 도움말에 적혀 있지 않습니다.

  • 첫째: name 줄이 ask-before-start 그대로인지 봅니다.
  • 둘째: 고친 description이 요청한 두 가지, 곧 예약 실행처럼 답할 사람이 없을 때와 다섯 조건을 다 준 요청을 모두 빼는지 문장에서 찾습니다.
  • 셋째: Claude가 본문까지 다시 보여 주었다면 다섯 조건의 표, 순서 1~6, 지킬 것 세 줄이 처음 파일과 같은지 한 줄씩 봅니다.

하나라도 다르면 Claude에게 어느 줄이 바뀌었는지 보여 주고 되돌리게 합니다.

고친 description에서 눈여겨볼 곳은 마지막 문장입니다.
"~에는 쓰지 않는다"처럼 빼 둘 때를 문장으로 적었습니다.
켜질 때만 적은 description은 그 밖의 경우를 Claude가 짐작하게 둡니다.
빼 둘 때를 적으면 그 짐작이 줄어듭니다.

그래도 Claude가 스스로 적었듯 이 문장은 판단의 근거일 뿐 보장은 아닙니다.
Skill이 실제로 그렇게 움직이는지는 시험으로 확인해야 합니다.

고친 Skill 다시 저장하기

대화에서 기존 Skill을 고치는 방법은 지금처럼 Claude에게 고쳐 달라고 요청하는 것입니다.
대화 옆에 Skill 파일이 열려 있으면 바꿀 글을 골라 Edit with Claude를 클릭해 고칠 수도 있습니다.

⚠ 확인 필요 Pro 데스크톱 앱 Windows 대화에서 Skill 파일이 대화 옆에 열리는지

고친 Skill은 처음 만들 때처럼 다시 저장해야 계정에 반영됩니다.

⚠ 확인 필요 고친 Skill을 다시 저장하는 버튼 이름과, 저장하면 Customize > Skills의 ask-before-start가 고친 판으로 바뀌는지

▲ 고친 ask-before-start를 다시 저장하는 화면

① 고친 description이 화면에 보이는지 확인합니다.
② 저장 버튼을 클릭합니다.

저장한 뒤 Customize > Skills에서 ask-before-start를 열어 description이 고친 문장으로 바뀌었는지 봅니다.
바뀌지 않았다면 이 대화를 지우지 말고 두었다가, 17강에서 고친 SKILL.md를 파일로 저장하고 폴더째 묶어 다시 올리는 방법으로 반영합니다.
아래 다시 보내기도 그때 합니다.

다시 저장해 반영했으면 시험지에서 다섯 조건을 모두 준 요청을 Project 밖 새 대화에서 다시 보냅니다.
이번에는 생각 표시에 ask-before-start가 보이지 않고 바로 문서를 만드는지 봅니다.
결과를 시험지 옆에 "고친 뒤"로 한 줄 더 적습니다.

예약 실행에서 이 Skill이 빠지는지는 19강에서 예약을 만들 수 있게 된 뒤에야 볼 수 있습니다.

⚠ 확인 필요 직접 만든 Skill이 예약 실행에서 켜지는지와 고친 description이 그때 지켜지는지

증거 계약

GitHub에서 연 hwpx SKILL.md의 "공통 안전 수칙"을 내려 읽으면 visual_review_required=true라는 낱말이 나옵니다.
9강에서 Claude가 HWPX 양식을 채운 뒤 검사 보고에 적던 그 낱말입니다.
그때는 Claude의 보고로만 보았지만, 이 낱말은 Skill의 문장에서 나온 것입니다.

같은 SKILL.md에서 "증거 계약"으로 시작하는 줄을 찾습니다.
그 줄은 visual_review_required=true이면, 화면으로 확인했다는 기록(observed_pass)과 화면 캡처 파일의 경로를 갖추기 전에는 문서를 바로 내도 된다고 말하지 않는다고 적습니다.
9강에서 Claude가 "직접 열어 확인해 달라"고 보고한 것은 이 한 문장을 읽고 따랐기 때문입니다.
Skill의 문장이 Claude의 행동을 바꾼 것을 여기서 볼 수 있습니다.

참조 인덱스

SKILL.md 끝의 참조 인덱스에서는 references 파일이 읽히는 때를 봅니다.
앞에서 본 것처럼 references 폴더의 파일은 일하다가 Claude가 그 파일이 필요하다고 판단할 때만 읽힙니다.
그래서 인덱스의 줄마다 파일 이름 뒤에 그 파일이 다루는 일이 적혀 있습니다.
예를 들어 official-document-rules.md 줄에는 공문서의 항목 표시와 날짜 규칙을 다룬다고 적혀 있습니다.
공문서를 만들 때 Claude가 이 파일을 열게 하는 것도 이 한 줄의 문장입니다.

지시를 어디에 둘까

오늘 한 일을 돌아보면, 조건을 묻게 하려고 쓴 것은 코드가 아니라 문장 몇 줄이었습니다.
Instructions에도, 프로젝트 지침에도, Skill에도 우리는 Claude가 읽을 문장을 썼습니다.
다른 것은 그 문장이 언제 읽히느냐입니다.

키오스크 대화마다 늘 맞는 것은 14강처럼 Project에 두고, 문서를 만들 때처럼 특정 일에만 필요한 것은 Skill에 둡니다.
그러면 같은 지시를 요청마다 되풀이하지 않아도 됩니다.
그리고 Skill이 언제 켜질지를 정하는 것도 description이라는 한 문장이므로, 켜질 때만이 아니라 빼 둘 때까지 문장으로 써야 합니다.

📌 정리 문서를 만들 때처럼 되풀이되지만 늘 필요하지는 않은 지시는 Skill에 둡니다.
Skill은 코드가 아니라 Claude가 읽는 문장입니다.
Claude는 description만 보고 Skill을 켤지 정하므로, 켜질 때와 빼 둘 때를 함께 문장으로 씁니다.
